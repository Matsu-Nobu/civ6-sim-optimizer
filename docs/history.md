# 記録の範囲

この文書には、10/04 から 10/18 までの作業を、日付ごとに記載する。次のセッションの Claude が、何をどこまでやり、何が失敗し、何が残っているかを、会話の記録なしで把握できることを目的にしている。数値はその日の測定の値で、別の日の数値とは、条件が同じときだけ比べられる。作業中に書き足した元の記録（`notes/plan.md`）は、10/18 にこの文書へまとめて消した。

# 10/04〜10/05 記録の準備

ゲームのオートセーブを残す数を 1000 個に増やした。設定は `%LOCALAPPDATA%/Firaxis Games/Sid Meier's Civilization VI/UserOptions.txt` にあり、元の設定は同じ場所の `.bak` に残してある。10/05 の対局で、31 個のセーブが残ることを確認した。

セーブ解析には `third_party/civ6-savegame-parser`（TypeScript）を使う。動かすための Node.js 22 は `tools/` に入れた。読める項目は `docs/design/save_data.md` にある。都市の食料の蓄えは読めない。

ゲームは、mod を適用した後のルールを `Cache/DebugGameplay.sqlite` に書き出す。BBG の SQL を自分で解釈せず、このデータベースのコピーを `data/rules/` に置いて使うことにした。

ローマの対局（`data/saves/game_20261005`、T1〜T31）を記録し、シミュレータの状態の設計を `docs/design/simulator.md` にまとめた。産出の静的な計算は、T3〜T31 の全都市でゲームと一致した。

# 10/06 効果の計算の仕組み

ゲームの効果（政策、建物、総督などがもたらす補正）を、個別に実装するのをやめた。ルールの表の modifier を、効果の出どころ、効果を受ける集合、適用の条件、効果の種類の順に解く汎用の仕組みに置き換えた。あなたが、場当たりの修正ではなく、ゲームの要素を体系的に扱う方法を求めたためである。

ルールの表のうち、扱っていない効果の種類・表を一覧にするスクリプト（`python_legacy/scripts/check_coverage.py`）で、未実装は 0、範囲外として理由付きで外したものが 495 になった。自動で 104 ターン進めた対局（`game_auto2`）を検証のデータにした。

# 10/07 Rust への移植と対局の再現

探索を速くするため、シミュレータと探索を Rust（`optimizer`）に移し始めた。計画の出発点と、シミュレータが計算できない出来事（ひらめき、使節、時代、他のプレイヤーが建てた遺産）は、分析する対局の記録から取ることにした。

ユニットの移動の規則と偉人を計画に入れた。移動の規則は、あなたが確認した内容（移動力が足りないときは、満タンのときだけ 1 マス進める、など）に従った。

ゲームの中で計画を自動で打つ mod（`game_mods/Civ6EconAutoplay`）で、計画をゲームの中で再現した。T8 ごろまで再現できたが、自動終了の処理でゲームが落ちた。以後、ゲームは自動で終了させず、起動の前にあなたの了承を得ることにした。

# 10/08 Rust 版への一本化と検証の方式

Rust 版だけを保守し、Python 版の `civ6sim` は対局データを作るときだけ使うことにした。対局データは `python_legacy/scripts/export_problem.py` が作る。

## 再現の検証

1 ターンずつ検証する方式（`civ6opt validate`）にした。各ターンのセーブの状態から、記録された選択で 1 ターン進め、次のセーブと比べる。差は次のターンに持ち越さない。セーブに無い情報（完成の余り、購入か繰り越しか）による差は、セーブの不足として分類する。

伐採の計算、交易商の本拠地の選び方、部族集落で得た交易商の扱いなどを直し、ローマ戦（`rome_20261007b.json`）の T60 までの再現の差は +1.2% になった。

## 探索の手法と不具合の修正

局所的な作り直し（`civ6opt lns`）と、揺さぶりと作り直しの繰り返し（`civ6opt ils`）を作った。決定の候補を確率で選ぶ手法（NRPA）は、既定の方針から始めると点数 8000 前後で失敗した。

ビルドを musl から glibc に替えた。musl 版はスレッドを作り直すたびにメモリを失い、15GB で強制終了していた。

決定の番号のずれ、延長評価で開拓者を作る問題など、探索の設計上の欠陥を直した。これより前の探索の結果は、欠陥を含むので比較に使わない。

# 10/11 探索の手法の比較

4 つの手法を、2 つの出発点と 3 つの乱数の種で 30 分ずつ比べた（`optimizer/scripts/compare_methods.sh`）。結果は [reports/search_methods.md](reports/search_methods.md) にある。遺伝的アルゴリズムの一種が平均で最良だったが、出発点ごとの行き着く先がそろわなかった。

長い探索が数時間に 1 回、glibc のヒープの検査で止まるようになった。3 本の探索が 0.03 秒以内に同時に止まったので、原因はプログラムの外にあると判断した。対策として、`optimizer/scripts/long_ma.sh` は保存した最良の計画から自動で再開する。

あなたの指摘で、手法の候補を手元にある手法から選び、問題の構造から考えていなかったことが分かった。以後、問題の性質を書き出し、合う系統を調べ、過去に試したことを確認してから候補を決める。

# 10/12 ロールアウトと目的の確定

各決定の候補を順に試し、良い変更を変化がなくなるまで取り込む手法（`civ6opt rollout`）を作った。3 つの出発点のすべてで、前日の最良の手法を上回った。ただし、行き着く先は出発点によって最大 27% 違った。

目的を、食料と生産の合計の最大化に決めた。ローマ戦では、T85 に内燃機関、T90 に全体主義を終えることを条件にした。軍事の強さは点数にしない。

# 10/13 フランス戦（10/13）の分析

マルチ戦（`game_20261013`、プレイヤー 8 がフランス）を対局データ `france_20261013.json` にした。T30 までにキャンパス 3 つ・投石兵・弓兵・社会制度 6 つを条件にして詰めると、T30 の累計はあなたの 964 に対して 983〜992 だった。

この分析で、評価の穴が 2 つ分かった。文化を条件にしないと、探索はモニュメントを削る。延長評価を 10 ターンにすると、序盤の伐採を過大に評価する。条件の指定に、社会制度の数（`civics:N`）と、伐採を許すターン（`--no-harvest-before`）を加えた。

# 10/14 序盤の定石と揺さぶりの探索

首都の序盤を簡略化したモデルで、タイルの選び方、偵察兵、開拓者の数を調べた。結果は [reports/opening.md](reports/opening.md) にある。

決定を 1 つ変えて、その後の 8 ターンをロールアウトで詰め直す探索（`civ6opt irollout`）を作り、90〜150 分ずつ比べた。序盤の決定を変えた計画は、3 回試して一度も採用されなかった。序盤を 1 手変えると後ろの計画が噛み合わず、点数が大きく下がる（例 32368 から 4164）ためである。

# 10/15 フランス戦（10/14）とコーサーの作戦

マルチ戦（`game_20261014`、プレイヤー 5 がフランス）を対局データ `france_20261014.json` にした。あなたのプレイを再生する処理を直した。記録で働いたタイルが別の都市の持ち物なら受け渡し、労働者の行動と区域の位置は記録どおりにする。再生の差は、T30 で ±0.0%、T45 で −3.0% になった。

記録で購入以外に減った金（味方に渡した金、T2〜T45 で約 530）を、どの計画からも差し引くオプション（`--gold-out`）を加えた。

あなたから、フランスの作戦の要は、城と傭兵を終えて騎乗兵をコーサーに上げる時期だと聞いた。以後、フランスの探索はこの時期と騎乗兵の数を目標にしている。

あわせて、文化と科学の進み方を調べた。BBG では、ゲームの時代が古代のうちに古典時代の社会制度を研究すると +20%、古典時代に古代の社会制度を研究すると −20% のコストになる。ゲームの時代は T31 の開始時に古典時代に変わる。城のひらめき（政体の 2 段目が必要）は取れない。防御戦術の前提に、遊びと娯楽がある。

# 10/16 練習用の mod と騎乗兵の探索

## 練習用の mod

ローカルのマルチプレイで練習するため、`~/civ6-practice-panel/PracticePanel` を作った。ひらめきの発動、戦略資源と贅沢資源と金の追加、味方の公務員制度の完了をボタンで行える。人間が 2 人以上いるゲームでは画面を隠す。mod がセーブに記録されるよう、`AffectsSavedGames` を 1 にした。ゲームが動いている間に Lua を書き換えると画面が壊れるので、ゲームを閉じてから編集する。

## 味方の金と贅沢資源

`--team` を加えた。味方に渡した金を差し引き、記録の快適性から、味方からもらった贅沢資源の数（0〜6）をターンごとに推定して加える。

## 騎乗兵の探索

`--require` に技術・社会制度・偉人の種類を、`--reward` に加点を加えた。将軍の条件が満たされない不具合（偉人の一覧から将軍が漏れていた）を直した。罰点が軽いと探索が条件を捨てて騎乗兵を作ったので、罰点を 5000 にした。

T43 までに城・傭兵・将軍を条件にした探索では、騎乗兵 9 体の計画（`data/search/mil/max.json`）ができた。条件の数で騎乗兵を必須にした探索（`k6`〜`k15`）は、どれも条件を満たせなかった。この原因は 10/17 に分かった。

10/14 の対局では、古典時代の将軍は T34、T38、T39、T41 に他のプレイヤーに取られていた。

## 練習の対局の分析

10/16 の練習の対局（`game_20261016c`）を分析した。城は T45（T44 に通貨へ 1 ターン寄り道しなければ T44）、将軍はハンニバルを T37、騎乗兵は T44 に 9 体、T46 に 13 体だった。4 都市がすべて首都の近くに固まっていて、敵の都市まで 11〜16 マスあったので、攻撃が逐次投入になった。

# 10/17 局所解からの脱出とペルシャ戦

## 罰点が守られない原因

既存の計画を今のシミュレータで評価し直すと、満たせていないのは T43 までの傭兵だけだった。足りない量は 1.5〜8% で、騎乗兵を作らない計画でも足りなかった。期限を T44 にすると、`max.json` はすべての条件を満たした。罰点が効かなかったのではなく、条件がほぼ満たせないものだった。

## 後ろ全体の詰め直し

T30 までの決定を 1 つ変え、後ろ全体を変化がなくなるまで詰め直す試験をした。36 例のうち 6 例が、それまでの最良の計画を上回った。この設定（`irollout --window 50 --passes 20 --kick-to 30`）で 1 時間探索すると、T44 の騎乗兵は 29 体になった（`data/search/nest/from_rec.json`）。結果は [reports/france_courser_spike.md](reports/france_courser_spike.md) にある。

## 皇帝近衛までの見通し

軍事科学までの技術と、皇帝近衛を作るための前提を調べた。10/14 の対局では軍事科学が T68 で、占領で都市が 11 に増えていた。占領しない前提で軍事科学を T65 に必須にした探索（`data/search/nest/ms65.json`）では、T65 に研究が約 3 割残った。

## 条件の判定の追加

探索プログラムに次の機能を加えた。

| 機能 | 内容 |
|---|---|
| 判定のターンの指定 | `--require X:N@T` で、条件ごとに判定のターンを指定できる。T44 の騎乗兵と T67 の軍事科学を同時に条件にするために作った |
| 条件の表示 | `run` が、条件ごとに満たしたかと罰点を表示する |
| 同盟国への交易路 | 同盟国の都市への交易路に、研究の同盟の科学（出発都市に +2）を加える。同盟国は記録の交易路の行き先から推定する（10/14 の対局ではオーストラリア） |
| 都市を建てる場所 | 他のプレイヤーの都市から 3 マス以内には建てない |
| 偉人の時代の指定 | `GREAT_PERSON_CLASS_GENERAL>ERA_RENAISSANCE` のように、偉人の時代を絞れる |
| 建物の条件 | `BUILDING_TERRACOTTA_ARMY` のように、建物を条件にできる |
| 記録で取った偉人 | あなたが記録の中で取った偉人は、計画が取らなければ、次のターンに誰かに取られたとする |

この条件で 2 本の探索（`data/search/ms67`）を始めたが、14 分ほどで WSL が落ちて止まった。

MemTest86 の 4 周の検査は合格した。続けて、Windows の上で直接負荷をかける Prime95 を 11:17 から 1 時間の予定で回している。

# 途中になっている作業

フランス戦で、T44 の騎乗兵と T67 の軍事科学を両方条件にした探索（`data/search/ms67`）は、出発点の計画 `a0.json` と `b0.json` まで作ってある。続きを回すと、`data/search/ms67/run.sh` が 80 分探索する。

ペルシャ戦の研究順の比較（`data/search/persia/run2.sh`）は、約 70 秒分の結果しかない。

どちらも、PC が落ちる原因が分かるまで回さない。Prime95 で Windows も落ちれば、ハードウェアか Windows 本体の問題として CPU の設定や電源を調べる。落ちなければ、WSL か Hyper-V の不具合として、WSL がメモリを Windows に返す仕組みを止めて同じ負荷の試験をする。
