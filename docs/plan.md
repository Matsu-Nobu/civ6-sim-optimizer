# 目標

対局の全体から、何が強い内政の打ち方かを探し出す。そのうえで、自分のプレイがどこで最適から外れていたか、最適ならどう打ったかを示す。

これまでの探索は、ある計画の近くを少しずつ直す局所的なものだけだった。探索の結果は出発点に依存し、シミュレータの穴を真っ先に突いた。全体から探すには、穴の無いシミュレータと、大量の対局を打てる速さと、違う方針の局面どうしを比べられる物差しが要る。この文書は、そこへ進む段階と、段階ごとの合格の基準を決める。合格の基準は、結果を見てから変えない。

# 段階と合格の基準

| 段階 | 中身 | 合格の基準 | 不合格のときにすること |
|---|---|---|---|
| シミュレータの穴つぶし | 分かっている穴を直し、計画をゲームで流して 1 ターンずつセーブと比べる仕組みで残りを洗い出す | 計画をゲームで流したとき、どのターンの食い違いも、規則の誤りではなくランダムな出来事で説明できること | 見つかった穴を直して、流し直す |
| シミュレータの高速化 | 1 局の計算のどこに時間がかかるかを測って削る | 延長なしの 1 局の評価が、今（約 0.3 秒）の 10 分の 1 になること | 削れない理由を数字で示して相談する |
| 物差しの学び直し | いろいろな方針の対局を大量に打ち、局面の価値のモデルを学び直す | 学んでいない方針の局面で、同じターンの 2 つの局面のどちらが良いかを 9 割以上当てること | 試せる回数が足りないのか、局面の特徴が足りないのかを数字で示して相談する |
| 全体からの探索 | 物差しを使い、手本の計画なしに初めから探す | 違う乱数の 2 回の探索が、同じ形の打ち方に行き着くこと | 探索の回数を増やす |

各段階は、前の段階に合格してから始める。手法を変えたくなったときは、どの基準にどれだけ届かなかったかを数字で示し、利用者に判断してもらう。

# シミュレータの分かっている穴（2026-11-01 時点）

- 探索の中で、工兵が道路を引かない。交易路とローマの能力による道路は、2026-11-01 に入れた。
- 伐採のあふれを消す規則は、記録との一致がわずかに悪くなった。どちらが正しいかは決まっていない。
- 計画をゲームで流して比べる仕組みが、まだ無い。

2026-11-01 に直した穴は次の 3 つである。都市を建てたターンの伐採が、記録の再現の伐採の合計から抜けていた。移動の計算が、伐採で消えた森や密林を、ゲーム開始時の地図のまま移動コスト 2 として扱っていた。移動の照合（`civ6opt movecheck`）では、労働者が 1 ターンでできないとされた移動が 4 局で 9 件から 1 件に減った。グラン・コロンビアの移動力 +1 は、BBG では政治哲学の後の戦闘ユニットだけが受けるので、内政のシミュレータが動かすユニットには関係しない。

# 計画をゲームで流す手順

計画をゲームで流して、シミュレータとゲームの食い違いを洗い出す手順は次のとおりである。出発点は、単独プレイの開始セーブ `EconPlanStart_mp1_T002` である。このセーブは、利用者のマルチ戦のセーブの見出しにある設定（BBG の BCY は首都だけで最大、蛮族なし、小屋あり、湖のマップ、超大サイズ、都市国家 18）で mod が作った。前に作った `EconPlanStart_rome2_T002` は、BBG の蛮族の設定が有効で BCY が無効なので使わない。このセーブには mod `Civ6EconAutoplay` が入っているので、ゲームでこのセーブを読み込むと、mod が計画を打ち、毎ターン `EconRun_<RUN_ID>_T<ターン>` の名前でセーブする。mod はゲームを自動で終了させない。

1. `tools/plan_lua.py` で、計画を mod の計画ファイル `Civ6EconPlan.lua` に書き出す。
2. mod の設定ファイル `Civ6EconRunnerConfig.lua` の `MODE` を `"plan"` にし、`RUN_ID` を決める。
3. mod の 4 つの Lua ファイルを、ゲームの `Mods/Civ6EconAutoplay` にコピーする。
4. 利用者がゲームを起動し、開始セーブを読み込む。最後のターンまで進んだら、利用者がゲームを閉じる。
5. 毎ターンのセーブを `data/saves/<RUN_ID>` にコピーし、記録として書き出して対局データを作る。
6. その対局データで同じ計画をシミュレータに打たせ、`tools/plan_diff.py` で毎ターンのセーブと比べる。

手順 6 で対局データを作り直すのは、ひらめきや使節や時代のような、シミュレータが計算しない出来事をゲームと同じにするためである。mod が決めない通知（使節など）でターンが止まったときは、mod が Shift+Enter と同じ操作でターンを終える。

# 計画をゲームで流して見つけた穴

2026-11-01 の実行（`econrun_mp1e`）を 1 ターンずつの照合にかけると、食い違いの無いターンは 62 ターン中 13 だった。単独プレイのセーブは、マルチ戦のオートセーブより 1 ターン後に書かれるので、記録のターンを 1 つ前に付け替えて照合している。

自然遺産のタイルの算出に、シミュレータが地形の算出を足していた（パンタナールで食料が 2 多い）。直すと、食い違いの無いターンが 44 になった。国境が広がる時期は、シミュレータが開始時点の国境の文化の蓄積を 0 から始めていたため、ゲームより 1 ターン遅れていた。T2 の開始では首都に 1 ターン分の文化があるとして直した。国境がどのタイルを取るかは、コミュニティの調査では重み付きのランダムで選ばれ、重みは公開されていない。記録の 371 回の広がりでは、368 回が都心からいちばん近い候補で、その中では贅沢資源、次にボーナス資源と見えている戦略資源が、一様なランダムよりはるかに多く選ばれていた。シミュレータはこの順で、いちばん選ばれやすいタイルを取る（記録の選択を当てる見込みは 42%、近さだけなら 20%）。残りの違いはランダムな出来事として扱う。残る食い違いは、T36 からの生産のわずかな差（政策を替えたターンのセーブの算出量）と、研究と社会制度の進み具合の差である。

# 2026-11-02 朝の状態

照合の結果は、計画をゲームで流した対局で 62 ターン中 56〜60 ターンが合っている（区間ごとに作り直した対局で 60）。合わないのは、開始セーブを読み込んだ T2 と、原因の分からない生産の進み具合の差が数ターンである。照合の過程で、セーブから政策を読む処理が空の枠で止まる穴（読み出しの側）を直した。

一方、伐採と製材所のルールは、ゲームではまだ試せていない。伐採と製材所を条件にした計画を流しても、ゲームでは伐採が 1〜5 回、製材所は 0 だった。開始時の計画は、国境のランダムな選択でゲームの状態からずれていく。区間ごとに計画を作り直す方法（tools/plan_loop.py）は、区間の境目で探索が研究や生産を切り替えてしまい、ゲームが弱くなった。

# 2026-11-02 午後の状態

利用者のマルチ戦の記録 5 局の照合は、T2〜29 では 140 ターン中 136 ターンが合うが、T30〜45 は 80 ターン中 56、T46〜65 は 98 ターン中 8 しか合わない。そこで、記録の中盤以降の食い違いから穴を探している。

見つけて直した穴は次の 3 つである。同盟は、セーブの記録から種類と期間を読み、その期間だけ同盟の種類ごとの交易路の算出を入れるようにした（以前は交易路の行き先を研究同盟とみなしていた）。他の文明からプレイヤーの都市に来る交易路は、シミュレータに 1 本も入っていなかったので、記録のとおりに入れた。伐採で品目が完成したときは、ゲームと同じく、そのターンのうちに次の品目に切り替えるようにした。T30 以降で、金の差の平均は 0.78 から 0.65 に、科学の差の平均は 0.69 から 0.62 に、生産の進み具合の食い違いの幅の合計は 3554 から 3269 に縮んだ。照合の食い違いの件数（414 件）は変わっていない。

セーブの都市の算出は、生産と科学では次のセーブの値の方がシミュレータに近く、前のターンに作った改良を含まないことがある。算出そのものの比較は目安にとどめ、穴の判定は照合の進み具合で行う。

# 2026-11-02 夜の状態

段階 1 の合格の基準は、利用者の承認を得て「T2〜45 で、T30〜45 の 90%（80 ターン中 72）」にした（T46 以降は、奪った都市と戦争の規則を入れてから測る）。5 局の照合で食い違いの無いターンは、T2〜29 が 140 ターン中 139、T30〜45 が 80 ターン中 72、合わせて 220 ターン中 211（96%）になり、基準を満たした（朝は 220 ターン中 192）。

いちばん大きな変更は、記録の 1 ターンの中の順番である。マルチ戦のオートセーブはターンの処理の前に書かれるので、2 つのセーブの間では、研究・成長・生産の処理が先に進み、そのあとでプレイヤーが労働者を動かし、物を買い、都市を建てる。シミュレータはこの順番に直した。あわせて、伐採で品目がその場で完成すること、伐採の余りの繰り越し、伐採の食料でその場で成長すること、同盟の種類と期間、他の文明から来る交易路、特性のユニットの付与、社会制度の完成で廃止された政策、着任したターンの総督とブーストで完成した技術の扱い、黄金時代のひらめきの量を直した。照合は訓練したユニットの数も比べ、セーブに整数でしか残らない保留の生産の端数による差は数えない。

T2〜45 で残る 9 ターンの食い違いは、差が 1〜2 の生産・食料と、ユニットの数 1 である。原因が分かっていて規則がまだ決まらないものは次のとおりである。費用 432 の社会制度のひらめきは、通常の量の式でも 1 ずれる（ペルシャ戦 T42）。1 ターンに複数の都市が労働者を作るとき、労働者の費用が上がる時点が都市の処理の順番と合わない（ペルシャ戦 T43〜45）。完成の余りが保留されずに消える例がある（フランス 10/24 戦 T11、ペルシャ戦 T44）。グラン・コロンビア戦 T40〜45 とローマ戦 T32 の差 1 前後の生産・食料は、まだ原因が分かっていない。

# 2026-11-03 の状態

5 局の T2〜45 の 220 ターンすべてで、シミュレータの計算がセーブの記録と一致した（T46〜65 は 98 ターン中 27）。

原因の調べ方として、ゲームにセーブを読み込ませる道具（`tools/probe_run.py`）を作った。この道具は、ゲームが計算した都市の算出・内訳・費用を書き出す。`--boosts` を付けると、全項目のひらめきを起こして量を測る。`--harvest` を付けると、セーブを書き換えて記録のプレイヤーを操作する側にし、ターンの処理の後に伐採・生産物の選択・購入・ターン終了を指定の順で行って、都市の状態を記録する。

この道具で確かめて直した規則は次のとおりである。ひらめきの量は、項目ごとに実測した実効の費用（`optimizer/src/boost_effective_costs.tsv`）に割合を掛けて切り捨てる。黄金時代の上乗せは割合に足す。次の生産物を選んでいない都市で先に伐採すると、その生産は消える。収穫の前にタイルを別の都市に移すと、収穫の生産はその都市に入る。贅沢品は処理の初めに配り直す。ほかに、使節・総督・守護女神の割増の効く時点と効き方を直した。

ペルシャ戦 T44 のゴルディオンでは、労働者の完成で出た余りの生産が、実際のゲームでは消えていた。一人用で同じセーブを動かすと、どの操作でも余りは残る。マルチ戦のターンの時間切れで、ゲームが生産物を自動で選んだときに消えたと推測している。シミュレータは、次のセーブで選んだ生産物の進み具合と保留がどちらも 0 なら、余りを消す。

# 2026-11-04 の高速化の結果

1 局の評価（延長なし、T65 まで）は、ローマ戦（`data/games/rome_20261021.json`、`--ally-supply`）で、そのゲームを探索して得た計画（`data/search/econ21f/e_online6.json`）では 0.171 秒から 0.063 秒に、記録の計画では 0.132 秒から 0.050 秒になった。測り方は `civ6opt bench` で、探索と同じ評価の関数を同じプランナーで 10〜20 回くり返したときの中央値である。合格の基準の 0.03 秒には 2 倍足りない。

残りの時間の約 3 割は、局面ごとに有効なモディファイアを判定し直してエンジン（効果の一覧）を作る処理で、1 局で約 270 回作る。残りの多くは 1 ターン分のシミュレーションである。さらに半分にするには、局面の差分だけでエンジンを更新する作りに変える必要がある。利用者の指示（本質的に削れないなら無理せず先に進む）により、ここで次の段階に進む。

効いた変更は、規則の表を引くハッシュを標準の SipHash から FxHash に替えたこと、地形・特徴・改良などの表の値を最初に 1 回だけ表にまとめたこと、エンジンを引く回数と鍵の計算を減らしたこと、労働者の行動候補を状態が同じ間だけ使い回したことである。保存されていた計画 64 本を、それぞれ探索したゲームで流した点数と、5 局の照合の結果は、高速化の前と完全に一致している。関数ごとの時間は、`samply record` で記録し、`tools/profile_summary.py` で集計できる。

# 2026-11-04 の価値の学び直しの途中経過

ローマ戦（`data/games/rome_20261021.json`）の計画 44 本について、`civ6opt valuerows` で、計画の周りの対局の局面と最終点数の組を集めた（`data/search/value3e`、`data/search/value3f`）。各対局は、ランダムに選んだターン C より前の決定だけを変え、C 以降の局面だけを記録する。C 以降は元の計画どおりに打つので、記録した局面から最終点数が一つに決まる。以前は C を設けず、局面より後で変えた決定の結果も点数に混ざっていた。

特徴量は 45 項目で、`optimizer/src/value.rs` の `features` と `features_extra` が計算する。その時点までに積み上がった点数（毎ターンの食料と生産の合計）を引いた残りの点数を、LightGBM に学習させた（`tools/value_compare.py --residual 22`）。

学習に使っていない計画 3 本の局面で、同じターンの 2 局面のどちらの点数が高いかを当てた割合は、次のとおりだった。全ターン平均は、検証用の 3 本の選び方で 86〜93% の幅がある。点数が最も低い計画と最も高い計画を検証用に回したときに 86% まで下がった。ターン別では、T42 以降が 90〜99% で、T2〜21 が 74〜90% である。

| 検証用の計画 | 別々の計画の組を含む場合 | 同じ計画の組だけの場合 |
| --- | --- | --- |
| `value3e` の 2・7・11 番 | 92.8% | 90.9% |
| `value3e` の 1・6・12 番 | 85.8% | 87.7% |

合格の基準の 90% は、検証用の選び方によっては満たしていない。

86% だった組み合わせを計画ごとに分けると、`econ21b/online1` が 93.6%、`econ21/guideK` が 87.3%、`econ21/guide0` が 82.2% だった。`guide` の 2 本は、44 本のうち 3 本しかない、ガイド付きの探索で作った計画である。次の 2 つを試したが、全体の当たり率は 87.7% から 88.0% にしか上がらなかった。

- 線形のモデルの予測を土台にして、その残りを LightGBM に学習させた（`--on-linear`）。
- 1 局で変える決定を最大 30 個に増やした対局を 1.9 万局集め（`data/search/value3g`）、学習に加えた。

データの量や幅ではなく、特徴量が、戦略の種類による局面の違いを捉えていないと考えている。
